# プロジェクト方針・運用メモ

2026-11-04にREADMEを簡潔にした際、元の詳細をここへ移しました。技術構成や公開先には当時の検討内容が含まれます。現在の概要は[README](../README.md)を参照してください。

ソフトウェア開発に関する「知らなかった概念・言葉・仕組み・構造」を、壁打ち、リサーチ、検証を通じて理解し、出典付きで蓄積する個人ナレッジプロジェクトです。

記事を知識の中心に置き、調査ノートに根拠と試行錯誤を残し、記事をもとにLT資料を作ります。後から検索・参照できることと、自分の言葉で他の人に説明できることを目指します。

## 基本方針

- 扱うのは、世の中に公開されている情報と、自分で行った検証・実験から得た体験です。社内情報は扱いません。
- 記事とLTスライドは、原則として一般公開します。社内LTは、成果を発表する機会のひとつです。
- 1記事で、ひとつの中心となる疑問に答えます。広がった疑問は、関連する別テーマとして残します。
- 「最初はどう理解していたか → 調べて何が分かったか → 実際に確かめてどう理解が変わったか」を大切にします。
- 公開情報で確認した事実、自分が観測した結果、そこからの解釈・仮説を区別します。
- 未解決事項や、期待どおりにならなかった結果も残します。分からない部分を断定で埋めません。
- 記事は理解の深まりに合わせて更新し、結論や前提に関わる訂正は履歴に残します。
- ブログ自体も学習の対象にし、HTML生成、アイランド、状態更新、検索などの仕組みを実験して記事に残します。

## 残すもの

| 成果物 | 残す内容 | 役割 |
| --- | --- | --- |
| 調査ノート | 疑問、仮説、出典、未解決事項、試行錯誤、次の作業 | 調査の途中から再開できるようにする |
| ナレッジ記事 | 問いへの答え、仕組み、図解、具体例、根拠、成立条件 | 後から検索・参照する中心にする |
| 検証記録・図解 | 環境、手順、結果、再現コード、説明用の図 | 主張を確かめ、理解を助ける |
| LT資料 | スライド、発表メモ、出典、元記事へのリンク | 他の人に伝える |

調査ノートの内容は、公開する記事に整理します。サイトに掲載しないノートでも、公開リポジトリへ保存した内容は公開されるため、公開可能な情報だけを置きます。非公開で残したい作業メモは別の保管先で管理します。

## 運用フロー

疑問 → 壁打ち → リサーチ → 必要な検証 → 記事化 → LT資料化 → 発表・公開後の更新

| 段階 | 行うこと | 残すもの・次へ進む目安 |
| --- | --- | --- |
| 1. 壁打ち | 疑問と現在の理解を出し、中心となる問い、調べる範囲、今回扱わない範囲を決める | 問いと仮説。理解したいことが一文で言える |
| 2. リサーチ | 一次情報を優先し、重要な主張ごとに根拠を確認する。資料の食い違いは条件・バージョン・時期まで調べる | 主張と出典の対応、適用条件、未解決事項。主要な答えを根拠付きで説明できる |
| 3. 検証 | 残る疑問や体験したい動作を、小さな実験で確かめる。実行前に目的、予想、結果の見方を決める | 実施日、環境、手順、観測結果、解釈。他の人が追試できる程度に条件が残っている |
| 4. 記事化 | テンプレートに沿って自分の言葉で再構成する。必要な図解や具体例を加える | 中心の問いに答え、根拠・観測・考察と説明の限界が分かる記事 |
| 5. LT資料化 | 聞き手、持ち時間、持ち帰ってほしいことを決め、記事から話す内容を選ぶ | Slidevのスライド、発表メモ、出典、元記事へのリンク。通して話し、時間と伝わり方を確認する |
| 6. 発表・公開後 | 質問、指摘、新しい検証、仕様変更を記事に反映する | 更新理由と変更内容。発表資料には発表日と参照した記事の版を残す |

### 調査・検証の区切り

- 中心の問いについて根拠を確認でき、残る不確実性を説明できたら、一度記事にまとめます。
- 派生した問いは、次のテーマとして記録します。
- 検証は、確かめたい問いがあるときに行います。すべての記事で実験を必須にはしません。
- 検証を省略した場合は、資料の確認に基づく説明だと分かるようにします。
- 測定や観測から結論を述べる場合は、条件と結果を残し、試していない環境まで一般化しません。
- 検証結果は条件を添えて記事に要約し、詳細な手順やログを別ファイルにした場合はリンクします。

### 作業を中断するとき

調査ノートの「現在地」を更新します。最低限、次の6点があれば再開できます。

1. 今回の問い
2. 現在の仮説
3. 確認できたことと対応する出典
4. まだ分からないこと
5. 試したことと結果
6. 次にやること

## 根拠と正確性の扱い

- 公式仕様、公式ドキュメント、原著論文、対象バージョンのソースコードなど、主張に合った一次情報を優先します。
- 解説記事などは理解の補助や調査の入口として使い、重要な主張は可能な限り一次情報までたどります。
- 壁打ちやAIの回答は下書き・調査の手掛かりとして扱い、回答そのものを技術的主張の根拠にはしません。
- 本文の重要な説明の近くに出典リンクと資料IDを付け、出典一覧と対応させます。
- 出典には、資料名、著者・発行元、URL・該当節、参照日を残します。公開・更新日、対象バージョンも分かる範囲で記録します。
- 引用と自分の要約・解釈が区別できるように書きます。
- 資料の内容、実際の観測、自分の考察を分けます。出典があっても、それだけで一般的な正しさが保証されるとは扱いません。
- 食い違いを解消できない場合は、両方の根拠と未解決の理由を残します。
- 記事の更新日と、情報の最終確認日を分けます。部分的な確認では、確認した範囲も記録します。
- LTの前には、リンクの有効性に加えて、主要な主張と適用条件を再確認します。

## 記事化・公開候補にする際の確認

| 観点 | 確認すること |
| --- | --- |
| 理解 | 資料を見ずに、中心の問いへの答えと仕組みを自分の言葉で説明できるか |
| 根拠 | 重要な説明を、出典や検証結果までたどれるか |
| 限界 | 成立条件、例外、未確認事項を説明できるか |
| 読みやすさ | 前提知識が分かり、図解・例・リンクが本文の説明と一致しているか |

説明できない箇所が見つかったら、その部分だけ壁打ち・調査に戻します。未解決の問いが残っていても、記事の結論を妨げず、その範囲が明示されていれば公開候補にできます。

## LT資料への展開

最初に「誰に、何分で、何を1つ持ち帰ってほしいか」を決めます。5〜10分の発表では、次の構成を出発点にします。

1. きっかけ：何が不思議だったのか。
2. 最初の理解：自分はどう考えていたのか。
3. 調べた答え：仕組みを図や具体例で説明する。
4. 自分で確かめたこと：検証結果と予想との違い。検証していないテーマでは具体例や比較を使う。
5. 分かったこと：理解がどう変わり、どこで役立つか。
6. さらに知りたい人へ：元記事と出典を案内する。

各スライドにも必要な出典を付け、記事とスライドを相互リンクします。記事は更新を続け、発表済み資料は発表日と参照した記事の更新日またはコミットを残します。発表済み資料を訂正する場合も、訂正日と内容を記録します。

## 検索・参照のために残す情報

記事のタイトル、本文、テーマ、日本語名・英語名・略語・別名、関連する記事へのリンクを蓄積します。現在のブログでは、Pagefindによる全文検索、種類・テーマの絞り込み、タグ別一覧、記事からシミュレーター・LT・検証記録への移動を利用できます。別名も索引へ含めます。関連記事や独立したLT一覧は、テーマが増えた段階で拡張します。

## テンプレートの使い方

- [記事テンプレート](../templates/article.md)：問いへの答えを公開記事として整理するときに使います。
- [調査ノートテンプレート](../templates/research-note.md)：壁打ちの開始時から、調査・検証・記事化・LT化の現在地を残すために使います。

テンプレートはコピーして使い、`{{...}}` を埋めます。任意の項目は必要なときだけ使い、記事に不要な案内文や空欄は公開前に取り除きます。記事とノートには共通のテーマIDを付け、相互にたどれるようにします。

保存先の運用案は、記事を `articles/<topic>.md`、調査ノートを `notes/<topic>.md`、LT資料を `talks/<talk>/` とします。これらのディレクトリは、最初のテーマを扱う際に必要に応じて作成します。

チャットでは、次のような単位で依頼できます。

- 「この疑問を壁打ちしたい」
- 「ここまでを調査ノートに整理して」
- 「未確認の点をリサーチして」
- 「検証方法を考えて」
- 「この記事テンプレートで記事案にして」
- 「この記事から5分のLT構成を作って」

最初の1テーマを通して、足りない項目や負担になる項目があれば、テンプレートと運用を調整します。
